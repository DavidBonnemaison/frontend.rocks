## TL;DR

`:has()` is a relational pseudo-class that styles a parent or preceding sibling based on what it contains or precedes. It eliminates `MutationObserver` hacks and manual `.has-error` class toggling while staying reactive to live DOM state.

## Under the Hood

For twenty years CSS only looked downward and forward because engines feared O(n^2) re-evaluations during the [Browser Rendering Pipeline](/concepts/browser-rendering-pipeline). Modern engines solved this with bloom-filter fast-rejects and targeted invalidation flags.

1. **Right-to-Left Anchoring**: When a child changes (e.g., a checkbox becomes `:checked`), the engine checks an ancestor bitmask to see if any parent listens to `:has()`.
2. **Specificity**: Like `:is()`, `:has()` adopts the highest [Specificity](/concepts/css-specificity-inheritance) in its argument list unless wrapped in `:where()`.
3. **Sibling Lookahead**: `.tab:has(+ .tab:hover)` styles the element *before* the hovered sibling.

```css
/* Highlight form field label when its input is invalid and touched */
.field:has(input:user-invalid) > label {
  color: #dc2626;
}

/* Lock page scroll when a modal checkbox or dialog is open */
body:has(dialog[open]) {
  overflow: hidden;
}
```

## Problem Genealogy

- **2000–2021**: Rejected repeatedly due to layout-engine invalidation cost; developers toggled parent classes in JS or React state.
- **2022–2023**: Safari, Chrome, and Firefox shipped optimized `:has()` with invalidation bitmasks, reaching Baseline Newly Available.

## Production Pitfalls

- **`:root:has(...)` over-invalidation**: Attaching `:has()` to `:root` or `body` with broad selectors like `:has(*:hover)` triggers wide style recalculations on pointer moves.
- **Nesting `:has(:has(...))`**: Nested `:has()` is disallowed by the spec and silently ignored.
- **When not to use `:has()`**: Avoid `:has()` on `:root` for high-frequency hover/scroll states; scope it to small local components like `.field` or `.card`.
